# Final CI State — v2.0.0

## Why this exists

Phase 71 is the final execution-evidence gate for SScribe v2.0.0. It must
never infer a passing release from a policy table that merely says what
*should* pass.

The tracked repository document is intentionally a **schema/template only**.
It must not be edited to embed the exact final commit SHA or final execution
statuses, because committing those values would create a new SHA and make the
evidence self-referential.

Strict release proof lives outside Git in the ignored `dist/` directory:

- `dist/final-execution-evidence.json` is the release engineer's exact-SHA
  execution-evidence input.
- `dist/final-ci-state-manifest.json` is generated by the verifier from that
  input plus the live checkout.

GitHub-hosted execution and local execution are treated separately:

- **SUCCESS** means the named GitHub job actually ran on the exact final SHA
  and completed successfully. Its evidence must be an `https://` execution
  URL.
- **LOCAL_PASS** is an explicit substitution for this release only when GitHub
  Actions did not start the job at all. The equivalent local command must have
  been executed against the exact final SHA, with a non-empty log stored under
  the repository and referenced as `local:<path>`.
- **UNAVAILABLE**, **FAILED**, **CANCELLED**, **SKIPPED**, and **MISSING** are
  not release-ready statuses for a required job.

The normal source/CI verifier checks this tracked contract structure. Strict
release certification is enabled with `SSCRIBE_RELEASE_CERTIFICATION=1`; in
strict mode the verifier requires a clean working tree (including non-ignored untracked files), binds the
untracked evidence `source_sha` to `git HEAD`, and requires every canonical
signal to be `SUCCESS` or `LOCAL_PASS` with independently inspectable
proof.

## Status convention

| Status | Meaning | Release-ready? |
|---|---|---|
| SUCCESS | GitHub job actually executed on the final SHA and passed. | Yes |
| LOCAL_PASS | Equivalent local gate executed on the exact final SHA because GitHub did not start the job; concrete local evidence is recorded. | Yes |
| UNAVAILABLE | GitHub did not start the job and no equivalent local proof is recorded yet. | No |
| FAILED | A required command or assertion failed. | No |
| CANCELLED | Execution was cancelled. | No |
| SKIPPED | Required execution did not occur. | No |
| MISSING | Required job/evidence is absent. | No |

Create `dist/final-execution-evidence.json` only after all tracked release
changes are committed and the checkout is clean. `dist/` is gitignored, so
this file can bind to the exact final SHA without changing it.

## How an independent auditor verifies this

For a normal source-contract check:

```bash
composer test:final-ci-state
```

For the actual release gate:

```bash
SSCRIBE_RELEASE_CERTIFICATION=1 composer test:final-ci-state
```

Then inspect both:

- `dist/final-execution-evidence.json`
- `dist/final-ci-state-manifest.json`

Verify that the manifest's `current_source_sha` equals `git rev-parse HEAD`.
Inspect every local log or GitHub URL referenced by the nine signals.

A strict green result plus nine shippable evidence rows is required before
tagging, subject to the remaining release blockers.

## What this contract does NOT cover

- Exact artifact identity is verified by Phase 72.
- Source/build public availability is tracked by Phase 70 blocker 18.
- Tag policy, branch policy, and WordPress.org submission remain separate gates.
